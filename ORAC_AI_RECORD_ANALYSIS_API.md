# ORAC AI Record Analysis API

**Status:** local backend implementation and automated tests only. The D: frontend does not yet expose this capability. The feature remains disabled unless `ORAC_RECORD_TRAIL_V1=enabled` is explicitly configured.

### 2026-10-19 Daily Time Sheet slice

Added `daily_timesheet` analysis for Admin, Management, Operations, Supervisor and the Technician who owns the sheet, matching the existing collection read boundary. It reuses server row validation and the Daily Time Sheet sign-off contract, reports status/date coverage and warns when a work date already appears in an approved Worksheet register. The overlap is only a duplicate-work warning, not a billing decision. The response excludes worker identity/contact details, descriptions, signature names/images, comments, raw validation messages and register identifiers.

### 2026-10-20 Contractor Log Sheet slice

Added `contractor_log_sheet` analysis for Admin, Management, Operations and Supervisor, matching the existing contractor-log collection roles. It reuses row validation and the monthly Worksheet's existing foreman/supervisor name-and-date sign-off check. It reports status/date, row count, validity, sign-off presence and the unweighted sum of recorded Normal/1.5/2.0 cells. It excludes contractor/worker names, grades, descriptions, order references, signature content, comments and raw validation messages. The package's separate weighted/payable-hours calculation is explicitly not used because that rule remains unconfirmed.

### 2026-10-20 Invoice settlement evidence slice

Invoice analysis now returns the server-calculated manual USD settlement summary
only to Admin, Management and Finance. The projection includes currency, invoice
total, paid amount, outstanding amount and payment count. It does not return
receipt rows, references, methods, idempotency data, request hashes, bank
clearance, tax/fiscal treatment, allocation, disputes, refunds, FX or accounting
export conclusions. Client Viewer continues to receive no settlement evidence.

### 2026-10-19 Standalone Field Worksheet (Timesheet) slice

Added typed `field_worksheet` analysis for Admin, Management, Operations, the Technician who owns the sheet, and its assigned Supervisor/dispatch Supervisor. This follows the existing field-worksheet collection scope; it does not add Client Viewer access, which remains on the separate client-timesheet route. The projection reports stored total hours and a validated Normal/1.5/2.0 breakdown when present, state/date, revision IDs, sign-off evidence completeness and the result/reason from the shared daily-source eligibility predicate. It flags invalid breakdowns and stored-total mismatches. It omits worker/client/supervisor identities, comments, attachments, signature images, rates and audit snapshots. A stored sign-off indicator is presence-only, and eligibility as a daily source is not invoice eligibility, commercial authorization or payment. The route remains behind `ORAC_RECORD_TRAIL_V1` and has no frontend integration.

## Purpose and scope

### 2026-10-19 Equipment Tag slice

Added an opt-in, deterministic Equipment Tag analysis for Admin, Management and Operations, matching the existing `equipment_tags` read guard. It returns recorded tag code/name/criticality/status and active state, plus resolved mine-site, plant and section identifiers/names. Findings identify missing or unresolved hierarchy links, inactive linked records, missing fields and case-insensitive duplicate tag codes. This checks stored master data only; it does not identify physical equipment, verify a QR label, establish service history or prove maintenance completion. Notes and audit snapshots are excluded. The route remains behind `ORAC_RECORD_TRAIL_V1=enabled` and has no frontend integration.

The health endpoint advertises `equipment_tag` only to Admin, Management and Operations. The exact role matrix is returned by `GET /api/ai/health`; use that runtime response as the authoritative current list rather than the earlier matrix below, which predates this slice.

### 2026-10-19 Material Usage slice

Added opt-in `material_usage` analysis for Admin, Operations, Supervisor and Technician, matching `addMaterials` and its dispatch-assignment guard. The summary reports quantity/unit and safe linked IDs, and checks a tracked usage record against its stock-out movement. It excludes free-text description, unit/total cost, actor and idempotency data. A matched ledger movement is not proof of physical consumption, client acceptance or invoice eligibility. Untracked/legacy usage is `not_applicable`, not reconciled. The exact role matrix is returned by `GET /api/ai/health`.

The original supported-type list predates the Equipment Tag, Material Usage and Field Worksheet slices. The current per-role list is exposed by `GET /api/ai/health`; use that endpoint as the runtime authority.

This is a deterministic, read-only record-analysis adapter for ORAC AI. It accepts an exact Quote, Dispatch, Field Worksheet/Timesheet, legacy Daily Time Sheet, Contractor Log Sheet, Invoice, client Purchase Order, Supplier, Maintenance Schedule, Equipment Tag, Material Usage, Catalog Item, Stock Item, monthly Worksheet Register or Client Service Request ID and uses the corresponding role-scoped evidence builder. It does not use an external model, accept free-form tool instructions, mutate business records, infer missing links, or substitute for a human workflow decision.

Quote analysis reports the existing role-visible Lead/Quote/PO/Dispatch trail. Dispatch analysis reports safe linked field-worksheet evidence and, only for roles holding the existing `viewDispatchTimesheets` permission, the safe projection of linked Timesheet review state. Standalone Field Worksheet analysis follows field-worksheet collection scope; Technician access is own-sheet only and Supervisor access is assignment-scoped. It reports sign-off evidence presence and the shared daily-source eligibility result without identities, comments, attachments, signature images or rates. Management does not receive rate-bearing Timesheet rows through Dispatch analysis. Invoice analysis is available only to Admin, Management, Finance and Client Viewer roles already allowed to read invoices. Client Viewer access is limited to invoices whose dispatch resolves to a quote belonging to that client's `client_id`; an unresolved or cross-client invoice returns 404. Invoice analysis includes the recorded invoice reference/status/time, PO status for internal roles already permitted to read POs, safe evidence IDs, link gaps and `payment_assessment: not_determined`. Admin, Management and Finance also receive a current server-calculated manual USD settlement summary; Client Viewer does not. The summary is not a bank-clearing, tax, allocation, dispute or accounting conclusion, and contains no receipt rows, references, methods or idempotency data. Monthly Worksheet Register analysis is available to Admin, Management, Operations and Supervisor, matching its existing register-view role boundary. It reports only approved worker/date coverage and allowlisted source-record IDs, flags overlaps with other approved registers, and treats every non-approved register as unconfirmed. Linked technician IDs are used where present; otherwise worker keys are represented by a one-way opaque digest. Output is bounded to 500 rows/references, with truncation disclosed. It does not expose names, hours, rates, amounts, comments or source contents, and it does not establish invoice readiness. Service Request analysis is available to Client Viewer for their own client-scoped request and to Sales/Operations for triage-scoped requests. It reports the stored status, urgency/date and verified site/equipment/Lead references; it checks conversion by reciprocal stored links and never treats an accepted request or requested date as a booking. It excludes service-need text, triage notes, names, contact data and audit snapshots. Audit action history is not returned because these roles do not have the existing audit-log permission. Purchase Order analysis follows the existing Admin/Management/Finance/Operations read roles and excludes PO reference text, amounts, client details and audit history. Supplier analysis follows the existing Admin/Management/Operations inventory read scope. It summarizes linked stock items, receipt counts and quantity totals by recorded unit, source-reference presence and each linked item's existing ledger reconciliation status, with bounded source IDs. It excludes contact details, raw source-reference text, costs, actor identities and free-text notes; a recorded reference is not document verification, a reconciled ledger is not physical stock proof, and this is not supplier performance or contract-compliance analysis. Stock-item analysis follows the same inventory scope and reuses `buildReconciliation` to report stored balance versus movement-ledger arithmetic, units, movement categories, and explicit ledger exceptions. It caps returned evidence references and findings at 200 but performs reconciliation over all movements for that stock item. Equipment Tag analysis follows Admin/Management/Operations asset-master access and checks recorded tag fields plus resolved site/plant/section links; it does not prove physical identity, validate QR labels or establish maintenance completion. Unlisted inventory/material entities and receipt-level/bank/accounting settlement analysis remain unsupported. The ordinary chat endpoint continues to decline individual-record lookup; the UI must not imply that arbitrary conversational lookup is available.

Clarification: the older overview's phrase “materials remain unsupported” refers to generic/material-wide analysis. The separately typed `material_usage` record described above is supported only with the role and dispatch scope stated here.

## Request

Authenticated JSON request:

```http
POST /api/ai/record-analysis
Authorization: Bearer <session-token>
Content-Type: application/json
```

```json
{
  "record_type": "dispatch",
  "record_id": "<exact dispatch id>"
}
```

`record_type` must be exactly `quote`, `dispatch`, `field_worksheet`, `daily_timesheet`, `contractor_log_sheet`, `invoice`, `purchase_order`, `supplier`, `maintenance_schedule`, `equipment_tag`, `material_usage`, `catalog_item`, `stock_item`, `worksheet_register` or `service_request`.

The actor and permissions come from the authenticated database account, never from request-body role/client fields. `GET /api/ai/health` reports the current role's `record_analysis.supported_types`: Admin (`quote`, `dispatch`, `invoice`, `purchase_order`, `supplier`, `maintenance_schedule`, `equipment_tag`, `material_usage`, `field_worksheet`, `catalog_item`, `stock_item`, `worksheet_register`); Management (same except `material_usage`); Operations (`quote`, `dispatch`, `purchase_order`, `supplier`, `maintenance_schedule`, `equipment_tag`, `material_usage`, `field_worksheet`, `stock_item`, `worksheet_register`, `service_request`); Sales (`quote`, `service_request`); Finance (`quote`, `invoice`, `purchase_order`); Supervisor (`dispatch`, `material_usage`, `field_worksheet`, `worksheet_register`); Technician (`dispatch`, `material_usage`, `field_worksheet`); Client Viewer (`invoice`, `maintenance_schedule`, `service_request`). This follows the current collection/action scopes. Maintenance Schedule analysis follows `viewContracts`; Client Viewer is restricted to schedules whose linked contract belongs to the authenticated `client_id`. Sales may verify a submitted PO through its action endpoint but does not receive PO read/analysis access; Client Viewer PO submission is not a grant to read the PO collection. Field Worksheet analysis follows the generic field-worksheet collection boundary and does not add the separate Client Viewer timesheet route. Catalog analysis follows the existing Admin/Management catalog master-data boundary; stock and supplier analysis follow the existing Admin/Management/Operations inventory roles.

The role matrix above is a historical summary; the current health endpoint is authoritative. `daily_timesheet` is advertised to Admin, Management, Operations, Supervisor and Technician, with Technician own-record enforcement. `contractor_log_sheet` is advertised only to Admin, Management, Operations and Supervisor.

## Response

Successful Quote response data contains:

- `analysisId`, `mode` (`deterministic-evidence-summary`) and `generatedAt`;
- the requested Quote reference;
- `findings`, each marked as a gap or historical exception with a stable code;
- `evidenceRefs`, each containing a visible stage name, record type and source record ID;
- `limitations`, including that missing relationships are not inferred and which evidence is not checked.

Successful Dispatch response data contains the dispatch reference, PO status only for roles already authorized to read POs, safe field-worksheet and Timesheet projections, deterministic gap findings (including a recorded but unverified PO and kiosk entries that do not count as approved), `evidenceRefs`, and explicit limitations. Evidence lists are capped at 200 per source, with a truncation indicator. It does not expose PO value or assert dispatch authorization, work completion, invoice readiness, or payment.

Successful Equipment Tag response data is available only to Admin, Management and Operations, matching the `equipment_tags` collection guard. It returns recorded tag identity fields and resolved mine-site/plant/section identifiers and names. It flags missing or unresolved hierarchy links, inactive linked records, missing tag/name/criticality/status fields and duplicate tag codes (case-insensitive). Notes, audit snapshots and client/staff personal data are excluded. It does not identify a physical asset, validate a QR label, establish service history or prove linked maintenance was completed.

Successful Material Usage response data is limited to Admin, Operations, Supervisor and Technician and is further scoped to dispatches the actor may access under the existing assignment guard. It returns the usage ID, dispatch/catalog/stock IDs, quantity/unit, creation time and ledger-link status (`matched`, `mismatch`, `missing_movement`, `multiple_movements`, `unexpected_movement` or `not_applicable`), plus safe evidence references/findings. Cost, free-text description, creator, idempotency key/fingerprint and audit snapshots are excluded. `matched` means the linked movement is a single stock-out for the same stock item and recorded quantity; it does not prove physical consumption or billable/invoice-eligible use.

Successful Field Worksheet response data is limited to Admin, Management, Operations, the Technician who owns that sheet, or a Supervisor assigned on the sheet/dispatch. It reports the validated total hours and Normal/1.5/2.0 breakdown when available, stored status/date, prior/successor revision IDs, three sign-off-presence booleans, and the existing daily-source eligibility result and reason. It flags malformed breakdowns, total mismatches, incomplete recorded sign-offs, unresolved dispatch links, ineligible state and superseded records. It does not expose names, comments, signature images, attachments, rates, or audit history. Eligibility follows the current shared predicate and does not establish billability, invoice readiness, commercial authorization or payment; sign-off indicators reflect stored evidence presence only.

Successful Daily Time Sheet response data is limited to Admin, Management, Operations, Supervisor and the Technician who owns the sheet. It reports stored status and timestamps, entry-row count, distinct dates, current server validation result, sign-off-presence booleans and whether any date overlaps an approved Worksheet register. That overlap is an investigation warning only. It excludes worker/contact identity, row descriptions, signature names/images, comments, raw validation text and register IDs. It does not calculate payable hours, establish invoice eligibility, or authorize billing.

Successful Contractor Log Sheet response data is limited to Admin, Management, Operations and Supervisor. It reports status/date, in-use row count, validation result, the existing foreman-or-supervisor sign-off check and an unweighted total of recorded hour cells when valid. It does not reveal names, grades, descriptions, order references, signatures, comments or per-worker rows. No weighted/payable-hours estimate, roster match, source consolidation or invoice eligibility is inferred.

Successful Invoice response data contains the invoice reference, recorded status and generated time, role-permitted PO status, deterministic missing-link/voided-record findings, `payment_assessment: not_determined`, `evidenceRefs`, and explicit limitations. Admin, Management and Finance additionally receive the current server-calculated manual USD settlement summary: currency, invoice total, paid amount, outstanding amount and payment count. Admin and Management may receive linked dispatch and quote references; Finance receives invoice and permitted PO references only. Client Viewer receives only their own invoice projection and `settlement: { status: "not_available_to_role" }`; they receive no PO/dispatch/quote detail. The response does not expose invoice lines, receipt rows/references/methods, idempotency data, void reason, fiscal data or accounting conclusions. A stored settlement summary is not interpreted as proof of bank clearance or payment finality.

Successful Worksheet Register response data contains the register reference/state, `coverage_status`, up to 500 `{worker_ref, date}` coverage rows, allowlisted source `evidenceRefs`, deterministic overlap/gap findings and limitations. Coverage is asserted only for an Approved register. It is not proof that hours are billable, an invoice is ready, or a payment is due. Rows and references are bounded; `evidence_truncated` and an `EVIDENCE_LIST_TRUNCATED` finding disclose omitted output.

Successful Service Request response data contains only its stored status, urgency, requested date, verified site/equipment IDs, a deterministic next-step hint and scoped evidence references. Sales/Operations receive a conversion status and a Lead reference only when both the request's `converted_lead_id` and the Lead's `service_request_id` agree. Client Viewer receives no internal conversion link and only the request matching their authenticated `client_id`. Accepted means accepted for follow-up; a requested date is a preference, not a confirmed booking. Action history is explicitly marked not returned; this route does not bypass the audit-log permission.

Successful Purchase Order response data is available only to Admin, Management, Finance and Operations, matching the current `purchase_orders` collection guard. It reports the stored state, whether a reference exists, verification timestamp, amendment-required marker, and a linked Quote's ID/reference/state when that exact relationship resolves. It flags missing or broken Quote linkage, non-verified status, missing reference or verification timestamp, and a required amendment. It excludes PO reference text, amount, client details, verifier identity and audit history. Sales' ability to verify a client-submitted PO does not grant PO read access; Client Viewer submission likewise does not grant collection read access. A PO status marked verified is not by itself authorization for a particular dispatch or approval of an amendment.

Successful Catalog Item response data is available only to Admin and Management, matching the catalog collection guard. It returns the catalog code, name, category, unit, stored unit price, material grade and dimensions, plus references to linked stock-item IDs/codes. Missing code/name/unit, invalid stored price, missing stock link and an explicit inactive marker are reported as findings where applicable. The catalog model has no active-status field by default, so absence is represented as `not_statused`, not as active. Supplier identity, stock quantities, stock cost and unapproved free-text fields are excluded. A catalog price is master data, not proof of an accepted quote price, tax treatment, supplier cost or authority to purchase; linked inventory evidence is handled by the separate Stock Item analysis.

Successful Stock Item response data is available only to Admin, Management and Operations, matching the current stock-item and movement read boundary. It reports stock identity, unit, stored on-hand quantity, arithmetic ledger balance/movement totals/categories, reconciliation status, finding codes and movement/material-usage evidence IDs. It reuses the established read-only inventory reconciliation function. A “reconciled” result means the stored ledger arithmetic has no reported exception; it does not mean a physical count or supplier document was verified. Returned references/findings are capped at 200 with truncation disclosed. No movement rows, actor identities, cost or supplier names, or free-text source details are returned.

Successful Supplier response data is available only to Admin, Management and Operations, matching the existing inventory read scope. It reports the supplier ID/name and recorded lead-time days, stock items linked by supplier ID, receipt count and quantity totals grouped by recorded unit, whether each receipt has a source-document reference, and the existing ledger reconciliation status for each linked stock item. Evidence references and findings are capped at 200. It does not return supplier contact details, raw source-document references, costs, actor identities, notes or audit snapshots. A reference's presence is not document verification; arithmetic reconciliation is not physical stock evidence. This is not a supplier score, delivery-quality assessment, contract-compliance check or purchase recommendation.

Successful Maintenance Schedule response data follows the existing contract-view scope: Admin, Management, Operations and Client Viewer; a Client Viewer can access only a schedule linked to a contract for their authenticated client. It reports the stored frequency/date, linked contract reference/status/period and a verified equipment tag when its site chain resolves to the same contract client. It flags missing/broken links, invalid calendar dates, dates outside the contract period and a contract not in Draft/Active status. Period comparison occurs only for valid calendar dates. Notes, contract values, client/staff identifiers and creator identity are excluded. The date is not interpreted as overdue, and the schedule is not evidence that work was performed, completed or signed off; the route does not book work or send reminders.

The response intentionally excludes audit snapshots, monetary amounts, PO values, contact fields and free-text reasons. Quote roles only receive linked stages permitted by the existing record-trail policy. Dispatch visibility follows the dispatch collection and assignment policy; its Timesheet data separately follows `viewDispatchTimesheets` and Technician own-row filtering. PO analysis and status are shown only to Admin, Management, Operations and Finance. A role that cannot read a record receives the same `404` response as an unknown record.

## Errors and audit

- `401`: missing/invalid session, enforced by the existing protected API middleware.
- `403`: inactive or unsupported assistant account.
- `404 RECORD_ANALYSIS_DISABLED`: trail flag is off; unknown and role-inaccessible records are also non-confirming `404` responses.
- `400 INVALID_RECORD_REFERENCE`: missing/oversized ID or unsupported type (including payment or other non-listed inventory records).

Successful analysis writes one `AI_RECORD_ANALYSIS` audit row containing record type, visible target IDs, finding codes and generation time. It does not store user question text or source-record contents. Denied and malformed requests do not write an analysis audit row.
